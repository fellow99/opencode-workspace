# OC Desktop 整体规格（overall-spec）

> 技术无关的系统级规格。回答“系统做什么、为谁做、怎么算做完”。
> 实现细节见 [`overall-plan.md`](./overall-plan.md)、[`ARCHITECTURE.md`](./ARCHITECTURE.md) 与各模块 `plan.md`。
> 事实源：根 `README.md`、`docs/能力对照清单.md`、三个子工程的 README / 工程规划 / 规格。未实测项标 `⬜`。

---

## 1. 系统目的与目标用户

### 1.1 目的

OC Desktop 把开源 AI 编码代理 **opencode** 的桌面体验带到移动/桌面融合设备上，作为**本机应用**运行：

- 应用内自带服务端与 Web UI，不依赖外部服务器；
- 上游 opencode 的 Web UI 100% 复用，用户学习成本为零；
- 数据默认留在本机，只有模型 API 出网；
- 三个独立第三方版别覆盖 HarmonyOS 与 Android，同一上游基线、同一服务端形态、同一补丁与插件体系。

### 1.2 版别

| 版别 | 工程 | 运行形态 | 渲染形态 | 目标设备 |
|---|---|---|---|---|
| HarmonyOS Edition | `oc-desktop-ark` | 进程内 Node，无 Electron/Chromium | ArkWeb | 鸿蒙 2in1 / tablet |
| Electron on HarmonyOS Edition | `oc-desktop-hos` | Electron 37 主进程内 Node | Chromium（ArkWeb 为目标通道，当前未落地） | 鸿蒙 2in1 / tablet |
| Android Edition | `oc-desktop-android` | 进程内 Node，无内嵌内核 | 系统 WebView | 平板 / 折叠屏 / 桌面窗口；phone 可用 |

> Windows / Linux / macOS 使用上游官方桌面版，不在本工程交付范围内。

### 1.3 目标用户

| 角色 | 诉求 |
|---|---|
| 鸿蒙 PC / 平板开发者 | 在设备本地用自然语言驱动编码代理：读代码、改文件、跑命令、看 diff |
| Android 平板 / 折叠屏用户 | 在移动设备上获得接近桌面的编码代理体验 |
| 企业内网用户 | 代码与数据不出本机，只有模型 API 出网 |
| 现有 opencode 用户 | 同一套界面与工作流，无需重新学习 |

## 2. 核心能力（用户故事）

### 2.1 启动与使用

- 作为用户，我能安装并启动应用，看到清晰的启动阶段，而不是白屏或闪退。
- 作为用户，我能新建会话、发送消息，并看到**流式**回复。
- 作为用户，我能看到工具调用（读文件 / 改文件 / 搜索 / 执行命令）的过程与结果。
- 作为用户，我能对权限询问作出选择，控制代理可以做什么。
- 作为用户，我能切换模型、填写自己的 API Key。
- 作为用户，我能选择工作目录，让代理在我关心的项目里工作。
- 作为用户，我重启应用后会话仍在。
- 作为用户，我能查看 diff、分支与版本库状态。
- 作为用户，我能看到失败的确切原因（阶段 + 原因 + 日志），而不是猜。

### 2.2 版别差异

- 作为鸿蒙用户，我希望应用不携带 Chromium，满足上架合规；ark 版以 ArkWeb 渲染。
- 作为鸿蒙用户，我希望在没有系统 git 的设备上仍能使用版本库能力；三版均提供进程内 Git 插件。
- 作为 Android 用户，我希望能在应用内使用 pnpm；Android 版提供进程内 pnpm 工具。
- 作为用户，我希望三版的品牌、图标、版本号保持一致。

## 3. 功能需求

> 编号规则：`FR-<域>-NNN`。模块级细化见 `specs/<NNN>-*/spec.md` 的 `FR-<模块>-NNN`。

### 3.1 运行时（RUNTIME）

- **FR-RUNTIME-001**：应用 MUST 在一次启动内拉起一个本地服务运行时；MUST NOT 依赖外部服务器。
- **FR-RUNTIME-002**：应用 MUST 以可观测的阶段展示启动进度；任一步失败 MUST 落到可读错误页（阶段 + 原因 + 日志尾 + 重启提示）。
- **FR-RUNTIME-003**：运行时状态 MUST 区分“已投递”与“已就绪”；只有观测到就绪证据（就绪文件、健康检查或等价判据）才算成功。
- **FR-RUNTIME-004**：应用 MUST 保证单实例运行；重复启动不得产生第二个服务端或第二份数据库写入者。
- **FR-RUNTIME-005**：运行时崩溃 MUST 被记录并提示用户重启；应用 MUST NOT 假装可以原地重启运行时。
- **FR-RUNTIME-006**：应用 MUST 把可写数据目录、临时目录与工作目录映射到平台允许的沙箱位置，并在启动时显式设置。

### 3.2 服务与数据（SERVICE）

- **FR-SERVICE-001**：应用 MUST 在本机提供 HTTP 服务，并同源提供 Web UI 与 API。
- **FR-SERVICE-002**：服务端口 MUST 在运行时确定；MUST NOT 把固定端口作为产品路径。
- **FR-SERVICE-003**：服务就绪后 MUST 提供可被宿主观测的就绪证据。
- **FR-SERVICE-004**：应用 MUST 在本地持久化会话与消息；重启后数据 MUST 仍可读。
- **FR-SERVICE-005**：载荷 MUST 有完整性校验（哈希清单或等价机制）；校验不符 MUST 拒绝启动并说明原因。
- **FR-SERVICE-006**：应用 MUST 在不依赖外部进程的前提下提供文件读写、编辑、搜索与命令执行能力；平台不可得的能力 MUST 如实报告。

### 3.3 渲染与界面（UI）

- **FR-UI-001**：主界面 MUST 复用上游 opencode Web UI，MUST NOT 自造一套业务界面。
- **FR-UI-002**：界面 MUST 与服务同源；MUST NOT 依赖 CORS 配置、自定义协议或注入桥完成业务通信。
- **FR-UI-003**：本地存储（localStorage / IndexedDB）MUST 可用；不可用时 MUST 在诊断中说明。
- **FR-UI-004**：首屏加载前 MUST 显示应用内加载页；成功后 MUST 清理导航历史，避免返回键回到中间态。
- **FR-UI-005**：外部链接 MUST 交给系统浏览器处理；MUST NOT 在应用内打开任意网页。
- **FR-UI-006**：应用 MUST 提供返回键/导航语义，避免用户被困在抽屉、设置或次级页面。
- **FR-UI-007**：应用 MUST 在界面上提供 AI 生成内容标识或等价合规提示（按版别合规要求落地）。

### 3.4 身份与凭据（AUTH）

- **FR-AUTH-001**：本地服务 MUST 始终启用口令保护。
- **FR-AUTH-002**：口令 MUST 由宿主生成并跨启动稳定；MUST NOT 写入日志、崩溃记录或文档。
- **FR-AUTH-003**：界面首次加载 MUST 无需用户手工输入口令。
- **FR-AUTH-004**：口令不匹配 MUST 表现为可见失败，并提供重置/恢复路径。
- **FR-AUTH-005**：模型 API Key 等用户凭据 MUST 只存应用沙箱；界面 MUST NOT 回显完整凭据。

### 3.5 宿主能力（HOST）

- **FR-HOST-001**：应用 MUST 向服务暴露一组受控宿主能力（权限查询、目录选择、外链、通知等）。
- **FR-HOST-002**：未注册或未实现的能力调用 MUST 明确失败；MUST NOT 返回空值、假成功或导致崩溃。
- **FR-HOST-003**：目录访问 MUST 经用户授权或系统选择器导入；MUST NOT 假设用户目录可直写。
- **FR-HOST-004**：通知、后台保活等能力 MUST 如实标注可用性；默认关闭的能力不得伪装成已启用。

### 3.6 工作区与版本库（WORKSPACE / VCS）

- **FR-WORKSPACE-001**：用户 MUST 能选择一个工作目录作为项目根。
- **FR-WORKSPACE-002**：工作区切换 MUST 反映到服务端项目根与工具路径围栏。
- **FR-VCS-001**：应用 MUST 在不依赖系统 git 的前提下提供基础版本库能力（状态 / diff / 提交 / 分支）。
- **FR-VCS-002**：版本库凭据 MUST 存于沙箱且权限最小化；界面 MUST NOT 回显完整口令。

### 3.7 插件与扩展（PLUGIN）

- **FR-PLUGIN-001**：插件 MUST 只来自本地构建期物化；在线插件安装 MUST 默认关闭。
- **FR-PLUGIN-002**：插件加载失败 MUST 可见，不得静默跳过。
- **FR-PLUGIN-003**：插件不得突破工作区围栏、凭据边界或平台权限声明面。

### 3.8 版本更新（VERSION）

- **FR-VERSION-001**：三个版别 MUST 共享同一上游基线（当前 opencode v2.2.5 / `9bbb8ce18c`）。
- **FR-VERSION-002**：应用版本号 MUST 三版一致（当前 2.2.5 / `versionCode 20205`），版本号规则 MUST 固定。
- **FR-VERSION-003**：上游升级 MUST 通过新建补丁目录、重建载荷、跑 host 门禁与真机回归完成；MUST NOT 直接改历史补丁。

### 3.9 品牌化（BRANDING）

- **FR-BRAND-001**：应用显示名 MUST 为 **OC Desktop**；版别后缀只用于仓库/文档区分，不进入用户可见应用名。
- **FR-BRAND-002**：Web UI 标题、图标、启动页、关于页 MUST 收敛为 OC Desktop 品牌。
- **FR-BRAND-003**：应用 MUST 声明非官方第三方移植身份，并保留上游 MIT 许可与第三方许可清单。
- **FR-BRAND-004**：品牌化 MUST 有可执行守卫（标题断言、图标检查或等价检查），防止上游升级后漂移。

### 3.10 构建与发布（BUILD / DISTRIBUTION）

- **FR-BUILD-001**：构建 MUST 可复现：固定上游提交、固定工具链版本、幂等补丁、哈希校验。
- **FR-BUILD-002**：构建 MUST 有门禁：补丁基线、载荷完整性、host 冒烟、产物哈希；任一红门不得发布。
- **FR-BUILD-003**：Android 版 MUST 支持 tag 触发的自动构建与 GitHub Release；鸿蒙版当前为本地构建，后续 CI 按 `012-building-workflow` 补齐。
- **FR-BUILD-004**：签名材料 MUST NOT 入库；无签名材料时 MUST 明确产出 debug/unsigned 包并说明。
- **FR-BUILD-005**：发布产物 MUST 附带 SHA-256 校验值或等价校验信息。

### 3.11 合规（COMPLIANCE）

- **FR-COMPLIANCE-001**：应用 MUST 满足目标平台的上架合规要求（权限声明面、无内嵌内核要求、AI 标识、隐私说明、第三方许可）。
- **FR-COMPLIANCE-002**：受限权限 MUST 按真实需要申报，并与使用点一一对应。
- **FR-COMPLIANCE-003**：发布构建 MUST NOT 包含调试通道、探针开关或诊断端点。
- **FR-COMPLIANCE-004**：应用 MUST NOT 绕过平台签名、可执行内存控制或应用商店审核要求。

## 4. 非功能需求

| 类别 | 要求 |
|---|---|
| 性能 | 冷启动到首屏可交互 SHOULD ≤ 15 s（设备差异大，按版别实测）；SSE 首事件 SHOULD ≤ 2 s |
| 可靠性 | 单次会话长跑 SHOULD ≥ 30 min 不崩溃；崩溃可取证、可重启恢复 |
| 体积 | 鸿蒙 ark HAP SHOULD ≤ 140 MB；hos 含 Chromium，体积显著更大；Android APK 按版本实测 |
| 安全 | 见 [`constitution.md`](./constitution.md) §四（S1–S5） |
| 可用性 | 所有失败态有中文可读文案；无空白页 |
| 可维护性 | 上游只读；补丁幂等；规格可追溯（FR → 代码 → 测试） |
| 国际化 | 界面语言由上游 UI 提供；壳层文案至少中文 |
| 离线 | 除模型 API 外不依赖外网；模型清单一律走内嵌快照 |
| 可访问性 | 依赖上游 UI 与平台 Web 组件的既有能力；v1 不额外承诺 |
| 证据 | 每条验收必须可观测；未实测标 `⬜`，不得计入已完成 |

## 5. 系统边界

### 5.1 在范围内

- 三个版别的应用宿主、运行时接线、渲染壳、鉴权、宿主能力；
- 上游 opencode 的构建、补丁、载荷投放、插件物化；
- 工作区选择/导入、进程内 Git、Android 进程内 pnpm；
- 品牌化、版本同步、构建发布、合规材料；
- 规格体系、能力对照、真机证据链。

### 5.2 不在范围内（v1）

- 手机专属 UI 与交互设计；
- 终端 PTY / 持久终端面板；
- 系统 git / `rg` / 外部 ELF 子进程；
- 本地 stdio MCP、LSP / formatter 外部进程；
- 在线插件安装（L2）；
- 后台常驻、开机自启、托盘；
- 云端账号、跨设备同步、团队协作；
- opencode 上游的二次开发与长期分叉。

## 6. 验收总则

- 每条 FR 至少对应一个可执行验收场景或模块 `test-cases.md` 用例。
- 验收陈述必须是**可观测事实**：HTTP 状态/字段、文件内容、屏幕截图、日志关键行、SHA-256、构建产物。
- 三版共同能力必须在父工程 `docs/能力对照清单.md` 或本规格中给出差异；单版独有能力由子工程规格定义。
- 未在真机验证的条目必须标 `⬜ 待验证`，不得写成“已完成”。
- 发布前必须通过 [`constitution.md`](./constitution.md) §五的质量门与代码评审批次。
